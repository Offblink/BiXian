# 用 VLM 做"看屏 → 挑一个编号"：生态调研 + 本机实测

2026-09-22。回答的问题：**能不能把 Jev/kev 那套"读候选概率的窄决策"搬到能看屏的 VLM 上，
用来替换 athand 里"挑哪个编号"这一环？**

结论：**能，本机可跑，比云端 SoM 快 7–24 倍，且不需要训练。** 但只有一条很窄的可行区间
（分辨率 ≤1024 长边），越界就掉进显存溢出、慢 400 倍。

## 一、生态里有什么（GitHub 调研）

**官方 Jev 是纯文本** —— `cobanov/awesome-jev` 里写得很直白："the hosted Jev model is text-only.
Browser, audio, image, and robotics projects supply extracted text or structured observations, or use
separate perception models." 多模态复刻单独列一节。同期有四份清单在维护同一批项目
（`AbdelStark/awesome-typesafe-jev`、`cobanov/awesome-jev`、`heyjunpenn/awesome-jev`、`yibie/awesome-jev`）。

### 与"VLM + Jev 机制"直接相关的

| 项目 | 底座 | 关键事实 |
|---|---|---|
| **PlayJev** | `Qwen3.5-0.8B-Base` **+ 自接视觉塔** | 读 448px 游戏帧 → typed option list → 每项一个概率；一次前向不生成；43 ms/move（H200）；2.2M 帧 + 3 轮 DAgger；Apache-2.0；权重公开 |
| **Laya Vision** | SmolVLM-256M | 图+文一次前向读 choice/noul；75.2% acc、**校准后 ECE 0.034** |
| **AnyJev**（Nokia 研究院） | 任何 transformers/vLLM 模型 | **不训练**；三档读出 raw/L0/L1；pip 可装；Apache-2.0 |
| **Jev Visual** | Qwen VL (MLX) | 候选直接打分，未校准（★238） |
| **minojev** | 冻结 Qwen3-1.7B + 0.8M 参数头 | 校准过的分布，ECE 0.024 |
| **JevForge** | Qwen3.5-0.8B | 全流程（合成数据→训练→校准→评测→serving） |
| **poorjev** | 零样本 NLI | 温度缩放 + conformal abstention，**ECE 0.170 → 0.071** |

### computer use 方向：现成的都走"抽文本"，不走视觉

`fastbrowse`（★95，"**picks instead of generating**"）、`jev-browser-use`（★363，"Jev clicks,
Codex thinks and verifies"，5–10× 快）、`Jev Browser`、`droidjev`（**"screenshot-free: AX → typed
pick → adb"**）—— 形态一致：

> **候选索引（结构） → 小模型挑一个 → 大模型规划/读文本 → 代码验证**

**这恰好就是 athand 的形状**，它只差中间那一格（`targets` 已经有了候选索引，`verify` 已经有了验证，
"挑"明确留给调用方）。**GUI 视觉路线没有现成实现**（视觉的 Luna 是 frontier 模型 + 规划，不是窄决策）。

### 关键的量化证据（BuilderIO/jev-computer-use-tests，严格后置条件）

| 方案 | Overall | Simple browser | Real-world browser | 桌面 computer use |
|---|---|---|---|---|
| Luna（视觉） | 55/57 **96.5%** | 100% | 80% | 5/5 100% |
| Hybrid（Jev 先 + 视觉兜底） | 96.5% | 100% | 80% | 5/5 100% |
| Jev Browser（结构化） | 18/52 **34.6%** | 42.9% | **0/10** | 未测 |
| Jev Ultrafast | 37.3% | 42.9% | 11.1% | 未测 |

成本：Jev **$0.000625/成功、3.62 s** vs Luna $0.0128、44.57 s。

**读法**：这是**端到端任务**成功率，不是"挑一个"的准确率——Jev 的失败形态是"点到了但没完成整个任务"
（作者原话 "passed 0/10 strict postconditions"）。所以窄决策的价值在**便宜/快**，不在**更准**；
长流程不能交给它。

### 读出方式：别自己搓，生态已经定论

AnyJev 的三档（Qwen3-8B / BANKING77 20 选一 / 300 条）：

| | raw | L0 | L1 |
|---|---|---|---|
| 需要标签 | 无 | **无** | 100–500 |
| 选项逆序后翻转 | 0.227 | 0.077 | 0.077 |
| 准确率 | 0.750 | 0.807 | 0.807 |
| ECE | 0.235 | 0.180 | **0.100** |
| ≤5% 错误下可自动化 | **7.7%** | **47.7%** | **54.3%** |

作者的核心判断：**"both are properties of the readout rather than of the model's knowledge"** ——
排序翻转与概率不可阈值化都是**读出的性质**，换个更好的模型解决不了，改读出方式可以，**且零标签**。

## 二、本机实测（Qwen3-VL-4B-Instruct + 合成 SoM 图）

环境：RTX 5070 Ti Laptop，`card limit 11.94 GiB`（物理 12.23，余量被桌面占掉）；
复用 kev 的 venv（transformers 5.17 直接认 `Qwen3VLForConditionalGeneration`），只补了 `torchvision 0.23.0+cu128`。

### 读出方式（照 PlayJev 做）

- 受限 softmax 在**最后位置**的候选编号 token 上
- **必须用 float32 读出**：bf16 logits 在 25–50 量级量化到 0.125，**会让选项打平** → 单独保存一份 fp32 的 head 权重重算
- 置信度用 Jev 公式 `(p_max − 1/K)/(1 − 1/K)`
- 编号槽验证：**单 token + round-trip + 无碰撞**（1–9 全是单 token ✓）
- 诊断：`allowed_mass`、`top_token`

### 分辨率：这是生死线

| 长边 | 图 | input tok | **视觉 tok** | 前向 | 峰值显存 | 结果 |
|---|---|---|---|---|---|---|
| native 2240 | 2240×1400 | 3226 | 3080 | **133 297 ms** | **14.55 GiB → 溢出** | #4 ✓ |
| 1568 | 1568×980 | 1657 | 1519 | 6074 ms | 11.49 GiB | #4 ✓ |
| **1024** | 1024×640 | 778 | **640** | **338–342 ms** | **10.37 GiB** | #4 ✓ |
| 768 | 768×480 | 498 | 360 | 535 ms* | 10.08 GiB | #4 ✓ |

\* 含首次 CUDA kernel 预热。

**视觉 token 的代价超线性**：640 → 1519（2.4 倍）时，前向 342 ms → 6074 ms（**18 倍**）。
**native 会溢出到主机内存 → 400 倍慢**（133 s）。1024 是这颗 VLM 在这张卡上的甜点。

### 准确率（1024，7 个问题）

```
HIT  #4  p=1.0000   点击发送按钮
MISS #7  p=0.4420   期望 #3  把文件发给 Blinvo      ← 唯一的错
HIT  #7  p=1.0000   查看家庭群的消息
HIT  #6  p=1.0000   撤回刚才那条消息
HIT  #2  p=1.0000   打开搜索框
HIT  #8  p=1.0000   把这条消息转发给文件传输助手
HIT  #9  p=0.9983   开始写一条新消息
→ 6/7，前向中位 342 ms，峰值 10.37 GiB
```

**最重要的性质：错的那个 p=0.4420，对的都是 1.0000** —— 错时置信度塌下来，**会被阈值拦成
UNDECIDED**。这与 kev 文本侧实测（对 0.93–0.97 / 错 0.21–0.23）行为一致：**没有"高置信选错"**。

### 换序敏感性（9 次轮转）

| 问题 | raw flip_rate | L0 |
|---|---|---|
| 点击发送按钮 | **0.000**（9/9 都是 #4，p=1.000） | #4 ✓ |
| 把文件发给 Blinvo | **0.125**（9 次里 1 次翻成 #5，p=0.973） | #3，**p=0.9994** |

**对比 AnyJev 在文本 LLM 上实测的 raw 0.227 —— 明显更低。**
推断原因：**SoM 的编号是画在框上的（空间锚定）**，列表顺序改变不影响"编号 4 在右下角那个框上"，
位置偏置被图像空间消掉了。这对 athand 特别有利——它的候选天然就是画了号码的框。

L0 的价值也量出来了：有歧义那题 raw 在某些轮转下 p 掉到 0.547（贴着阈值），L0 合并后 0.9994。
**所以 L0 是加固（成本 K 倍 = 3.3 s），不是必需品**；折中用 `max_permutations` 跑 2–3 次轮转。

## 三、怎么落地到 athand（唯一要改的那一格）

```
athand targets --hwnd N        →  编号候选 + 画了号码的 PNG      （已有）
   ↓  降采样到 1024 长边
本地 VLM 一次前向              →  每个编号一个概率 + 置信度        （新增，342 ms）
   ↓  过阈值
click --target K               →  athand 执行                     （已有）
   ↓  verify / ESCALATED       →  程序事实兜底                     （已有）
```

- 低于阈值 → `UNDECIDED` → **调用方走原路径**（agent 读图自己挑）→ fail-open，不替代任何东西
- **不需要训练**；AnyJev 的 backend 接口只有一个方法（`next_token_logprobs`），加 VLM 支持约 50 行；
  图像通道可用约定绕过（state 里放占位符，backend 解析后喂 processor）
- 若要把 L0 接上：用 AnyJev 的 `cyclic_shifts` + `marginalize(combine="logmean")`

### 对照表

| 方案 | 延迟 | 备注 |
|---|---|---|
| kev 文本（raw，5 问一请求） | **102 ms** | 候选有文字时用它，最便宜 |
| **本地 VLM @1024（raw）** | **342 ms** | 能看图；画面不出本机 |
| kev 文本 + L0（K=9） | ~0.9 s | 去偏 |
| 本地 VLM + L0（K=9） | ~3.3 s | 去偏 |
| 云端 SoM 挑号 | 2.4–8 s | 需上传真实画面 |

### 分工（显存决定的，不是偏好）

`kev-4B`(9.1 GB) 与 `VLM-4B`(9.7 GB) **装不下同一张 12 GB 卡**。要共存得把 kev 降到 0.8B（~1.8 GB）
或 4-bit。**候选有文字**（a11y 名/OCR 文本，athand 的多数情况）→ kev 文本档 102 ms；
**纯形状、要看布局** → VLM。

## 四、踩过的坑（会重复咬人的）

1. **`{"type": "image"}` 不带载荷会被静默忽略** → 模型只看到文本，`in_tok` 停在 139，看起来像"模型很弱"。
   正确写法 `{"type": "image", "image": <PIL>}`。
2. **bf16 logits 会让选项打平**（25–50 量级量化 0.125）→ 必须用 fp32 的 head 权重重算读出。
   这条不修会得出"模型没信号"的错误结论。
3. **`size={"longest_edge": …}` 的语义不是像素**，我猜错后图被缩成 2×2 个 patch（`vis_tok=1`），
   **三个分辨率给出完全相同的结果**——这本身就是识别它的线索。结论：**自己用 PIL 缩放**，别猜 processor 语义。
4. **Qwen 的 `size` dict 必须同时给 `shortest_edge` 和 `longest_edge`**（只给一个直接 ValueError）。
5. **FLORA 式教训**：单场景成功不足以下结论；单场景"失败"也不足以——先确认输入真的进去了。
6. **本机下载大文件的坑**：Flower 不可跨次续传（换网络/断连即丢全部进度）；ModelScope 直链是 302，
   测速必须 `-L` 否则量到的是重定向响应体；多连接有效（单连接 94 KB/s → 8 路 2.05 MiB/s）。

## 五、4-bit 量化实测（同日第二轮）

`BitsAndBytesConfig(load_in_4bit=True, nf4, double quant, bf16 compute)`，`bitsandbytes 0.50.2`。

**一句话：4-bit 在 1024 上不掉准确率、不涨延迟、显存砍一半，还把 native 从「溢出 → 133 s」
变成「不溢出 → 3.3 s」。**

| 长边 | bf16 前向 / 峰值 | **4-bit 前向 / 峰值** | 7 问（bf16 → 4-bit） |
|---|---|---|---|
| native 2240 | 133 297 ms / 14.55 GiB（溢出到主机内存） | **3254 ms / 8.98 GiB** | — → **6/7**（错的 p=0.9382） |
| 1568 | 6074 ms / 11.49 GiB | **1119 ms / 5.93 GiB** | — → 6/7（错的 p=0.9277） |
| **1024** | 342–353 ms / 10.37 GiB | **357–368 ms / 4.81 GiB** | 6/7（错的 p=0.4420）→ **7/7** |

- **空载权重 9.72 → 4.16 GiB**，加载 6–8 s（量化在加载时做，无额外成本）。
- **读出没被量化伤到**：1024 上 7 问全对；bf16 唯一错的「把文件发给 Blinvo」在 4-bit 下
  以 p=0.9853 答对。§8.1 担心的「head 反量化误差进 logits」在这一题上没有出现。
- **抬分辨率并不更准**：native 与 1568 都在同一题上错，而且是**高置信错**（0.9382 / 0.9277）——
  阈值拦不住，比 1024 上的低置信错更危险。**1024 仍是甜点**；量化买到的是「能抬分辨率」
  和「能和别的模型共存」，不是更准。
- **一条测量坑**：`tools\vlm_multi.py` 三档连跑时 4-bit @1024 量到 884 ms；把同一脚本、同一分辨率
  **单独**跑（`tools\run_multi_1024_4bit.py`）是 **368 ms**。差异来自同一进程里先跑过 native
  （分配器/KV 状态）——**别拿多分辨率连跑里的单点数字当延迟**。
- 复跑命令：`tools\run_sweep_4bit.py`（分辨率扫描）、`tools\run_multi_4bit.py`（三档准确率）、
  `tools\run_multi_1024_bf16.py` / `tools\run_multi_1024_4bit.py`（同条件对拍）。

## 六、接缝（已落地：`vlm-probe/vlm_pick.py`）

一行不改 athand 的独立脚本：`athand listing + 意图 + frame → 编号 或 UNDECIDED`，只打印不动作。

```powershell
# 单次（数据都在 cases\；--expect 是 athand 号，不是 our #）
& $py vlm_pick.py --listing cases\fixture-som.json --intent "点击发送按钮" --k 9 --expect 12
# 热循环：权重只加载一次（加载 8 s 比一次前向还贵），每行一个 json 请求
'{"listing":"cases\\fixture-som.json","intent":"点击发送按钮","frame":"cases\\bare.png"}' | & $py vlm_pick.py --loop
```

> 2026-09-23 目录重排：素材/产物进 `cases\`、实验脚本进 `tools\`，根只留 `vlm_pick.py` 与 `eyes.py`
> （地图见 `docs\VLM_PROBE.md`）。下文出现的裸文件名按这两条归属理解。

实测（`cases\fixture-som.json` + `cases\bare.png`，9 候选，4-bit @1024，峰值 4.81 GiB）：

```
loaded in 8.0s | edge 1024 | 4-bit
asked 9 candidates, forward 718 ms (total 800 ms), 640 visual tokens, peak 4.81 GiB
   our #4 -> athand #12   发送      p=1.0000  «点击发送按钮»     -> YES  click --target 12
   our #3 -> athand #4    Blinvo    p=0.9853  «把文件发给 Blinvo» -> YES  click --target 4
```

**默认分辨率已按 §七 改成 1536**（实测前向 1.0–1.3 s、峰值 5.82 GiB、映射仍正确）。
注意同一道「把文件发给 Blinvo」在 1536 下会以 **p=0.6464 选错 `#9 发送文件`** —— 与 §七 记录的
高置信错是同一现象：阈值 0.5 拦不住它，`--policy irreversible`(0.99) 才会拦成 UNDECIDED。

三个刻意的设计：

1. **编号由我们自己画**。读出是最后位置的受限 softmax，每个选项必须是**单 token**，
   而 athand 的真实编号跑到几十（`27. Blinvo` 是两个 token）。所以在 frame 上自己画 1..K
   （K≤9，红框 + 左上方白底数字，样式照 athand 的 `_mark_targets`），输出时再映射回 athand 的 n。
   实测映射正确（上面 our#4→athand#12、our#3→athand#4，编号是故意打散的）。
2. **不按有没有名字预过滤**。文本档必须丢无名候选；这里框是看得见的，形状候选反而正是 VLM 的价值。
   只丢"窗口外"和 source 白名单外的。
3. **fail-open**：peak 不过 policy 阈值就打印 UNDECIDED 并 `exit 2`，调用方走原路。

## 七、模型 × 分辨率矩阵（2026-09-23，4 张桌面 34 问）

### 为什么要重做 bench

第一版只有 `cases\som.png` 一张图 7 问、36px 标签——得出的是无意义的排序：同一道题在 4-bit 下
768/1024/1536 对、1280/1792/2240 错，非单调。更根本的问题：**在 36px 文字上分辨率根本不是变量**
（768 就全对），所以那个 bench 只可能得出"768 够用"。真实界面文字是 12–20px：

| 桌面 | 标签字号 | 问数 | 考什么 |
|---|---|---|---|
| `cases\som.png` | 36px | 7 | 大字近义词陷阱（发送 / 发送文件 / 撤回） |
| `cases\d_notepad.som.png` | 20px | 9 | 英文菜单，Search / Replace / Find Next 三连 + 无名文本区 |
| `cases\d_settings.som.png` | **14px** | 9 | 中文对话框字号，确定 / 取消 / 应用三连 + 无名搜索框 |
| `cases\d_browser.som.png` | **14px** | 9 | 英文浏览器外壳（第二张真实字号桌面，让"要 1536"不只靠一张图） |

生成器 `tools\make_desktops.py`（裸桌面 + listing + 由 `vlm_pick.annotate` 画的编号图 + cases，
编号只有一处实现）。两处踩过的坑：**编号字号改为按控件高度缩放**（原来固定 40px 的数字补丁压在
26px 高的按钮上会盖住标签）；**问题用标签匹配控制项时，两个无名控件会让 `.index("")` 静默取第一个**
（d_browser 的「click into the page content」期望被写成地址栏的 4 号 → 模型答对却记成错），
现在改成允许写索引，且标签歧义直接断言报错。

| 4-bit 高置信错 | 9 | 6 | 6 | 4 | 3 | 0 |

- **2B 的 4-bit 明显更差**（1536：27/34 vs bf16 32/34，高置信错 4 vs 1）。4B 上 4-bit 不掉分是因为
  冗余够多，**2B 没这个余量**：量化不是无条件免费，必须按模型分别量。
- 2B 最准是 bf16 @1536（32/34，608 ms，6.23 GiB）；**唯一"零高置信错"的点是 bf16 @1280**
  （31/34、516 ms、5.85 GiB）——当"宁可交回 agent 也别点错"的安全档很合适。

### 8B（只测得了 4-bit；bf16 的 16.34 GiB 装不下这张卡）

| 8B 4-bit | 768 | 1024 | 1280 | 1536 | 1792 | 2240 |
|---|---|---|---|---|---|---|
| 准确率 | 22/34 | **32/34** | **32/34** | 31/34 | **32/34** | — |
| 中位前向 / 峰值 | 329 ms / 8.73 GiB | **558 / 9.04** | 900 / 9.52 | 1449 / 10.20 | 2285 / 11.12 | **150–163 s/次**（溢出，abort） |
| 高置信错 | 9 | 2 | 2 | 3 | 2 | — |

- **8B 不如 4B**：8B 最好 32/34，而 `4B 4-bit @1536 = 34/34` —— 大一倍的模型在这个任务上**没换来分**，
  换来的是 1.4–2.6× 延迟、9–11 GiB 显存（4B 只 5.8 GiB）、以及 native 直接溢出。
  （手稿里"8B 4-bit ≈ 4.5 GiB"的估计是错的：实测峰值 9–11 GiB。）
- **native 的溢出是硬墙**：11.12 GiB @1792 还能跑（2.3 s），到 2240 就掉进主机内存，
  单次前向 **150–163 秒** —— 和当初 4B bf16 native 的 133 s 同一个病。
  可用区间是 **768–1792**，且 1792 已经没有余量。
- 结论：**这一档不值得换**；要更好就得走训练路线（PlayJev 那种），不是换更大的底座。

- **桌面图标这条路是通的**：`targets --hwnd <Program Manager>` 把 21 个图标全列成 a11y 候选（含名字），

本轮两次判据分叉得很干净——frame 说"变了 0.33 %"（52 个字只占屏幕 0.33 %），磁盘说"100 字节、内容一致"。

### 十之三、阈值机制：有，但没有"自动回退"（2026-09-23，B站一轮暴露）

**问题**：低于某个置信度会不会自动回退到 VLM？**答：阈值有，回退链没有 —— 回退被明确设计成调用方的事。**

**阈值表**（`bixian/policies/default.json`；`policy.py` 里同名 `DEFAULT_POLICY` 兜底；`vlm_pick` 直接
`from bixian import policy` 复用同一份，所以改 JSON 同时改文本决策与挑号）：

| 具名策略 | 阈值 | on_fail |
|---|---|---|
| `explore` | 0.20 | fail_open |
| `default` | 0.50 | fail_open |
| `irreversible` | 0.99 | fail_closed |

动作类映射 `read_file/score_memory→explore`、`write_file/stage_commit→default`、
`run_command/send_message/publish→irreversible`、**`unknown_class=irreversible`**（没声明类＝最严）。
阈值是**文件**里的、由标注集上的 risk–coverage 曲线**估**出来的，不搜参；换模型或温度要重估。

**语义**（`policy.py` 原文）：阈值属于**调用点**，服务只报概率；`--policy` 只能让决定**更严**；
概率过底线但没过策略时结果是 **UNDECIDED，永远不是 NO**。
挑号里 `confidence = (peak − 1/k)/(1 − 1/k)`（k=9 时先减掉 0.111 的随机基线）再比阈值。

**UNDECIDED 之后什么都不自动发生**：`-> UNDECIDED: caller keeps its own path (re-list, read the frame,
or a bigger model)`；bixian CLI 退出码表 `2: UNDECIDED - fall back, never guess`；`errors.py` 要求调用方
当成"没有决定"并回退到**自己的模型**。要"低于阈值回退到 VLM"，得在调用点接：
`vlm_pick(1.4 s)` → UNDECIDED → ①重列/读帧 → ②我自己的眼睛（微信那轮实测 8.5 s/次）→ ③问人。

**B 站那轮同时演示了两件事**：

1. **机制是对的，是我没尊重它**：第三次挑号日志原文 `peak=0.4987 confidence=0.436 threshold=0.50 → NO /
   UNDECIDED`，而我的 driver 忽略 `decision` 字段照样点了 `#13 新标签页`。**错在调用点**。
2. **阈值拦不住"自信的错"**：同轮选"搜索框"是 `peak=0.9939 → confidence=0.993 → YES`，但命中的是
   `TabStripComboButton`（浏览器标签栏），完全错。阈值过滤的是**不确定**，不是**错误**。

### 十之四、Chromium 页面在 athand 里不可寻址（B 站一轮的结构性结论）

浏览器里"挑个号点搜索框"这条路**根本不存在**，与模型好坏无关：

- Chrome 窗口的 listing：**60 个候选，全部 `source=a11y`，全部是浏览器自身 UI**（标签页/最小化/书签/地址栏），
  页面 DOM 一个都没有；`plausible()` 还会把覆盖全窗的那几条（渲染宿主）滤掉，于是可点的更少。
- `--force-renderer-accessibility` 重启**没变化**（仍 60/60 a11y）。Edge 同理：47 个候选、全是浏览器 UI。
- `click --name "搜索"` 会被 a11y 宽松匹配到**「标签页搜索」**并点掉（实测咬一次）——名字兜底在这里同样危险。
- 绕法（已验证可用的形状）：**自己 OCR 页面截图造候选**（`shot` → RapidOCR 106 个框 → 写一份
  `{"rect": 窗口矩形, "targets":[{n,name,rect,source:"ocr"}]}` 的**伪 listing**）→ 喂 `vlm_pick` 挑号 →
  再用 `click --name <那段 OCR 文本>` 落地。注意点击只能走 `--name`，因为 athand 的 `--target` 只认它自己的 listing。
- 更省事的结论：网页内容要走 `--name`/键盘（`ctrl l` + URL、Enter），别指望编号那一层。

### 十之五、两级眼睛落地：`eyes.py`（2026-09-23，用户确认的设计）

用户口述的拓扑：**一个 VLM 在后台调 bixian，bixian 是它的小眼睛；小眼睛不自信，就问背后的大眼睛。**
这一轮把它做成了脚本契约，而不是"调用方自己看着办"：

- `vlm_pick.py` 现在**每次都把喂给模型的那张图落盘**（`<listing>.som.png`），并在结果里加 `som` 与
  `options`（`our → athand n/name` 映射）。理由是硬性的：大眼睛必须看**同一套编号**，否则答案映射不回 athand 的号。
- `vlm-probe/eyes.py` = 两级接缝。tier1 起一个常驻 `vlm_pick --loop` 子进程；返回值：
  `{"tier":1,"decision":"YES","n":…}` exit 0 ／ `{"tier":2,"decision":"ESCALATE","som":…,"options":[…],"guess":…}` exit 3
  ／ 构造性失败（无候选、无图）exit 2。**tier2 从不替大眼睛猜**：它把图与选项表交上去就退出。
- 用法：`python eyes.py --loop --k 9 [--policy/--policy-file]`（真实作业用这个，权重只加载一次 13 s，之后 1.5 s/问）；
  单发 `--listing/--frame/--intent` 会付一次冷加载（实测 55.7 s）。

**实测（同一张 2560×1600 桌面图，k=9）**：

| 意图 | p | confidence | 结果 |
|---|---|---|---|
| 4 个 `.txt` 里随便哪一个 | 1.0000 | 1.000 | YES（自己就选了 `b-run2.txt`） |
| 5 个文件夹里随便哪一个 | 0.99995 | 0.99994 | 默认门槛(0.5)=YES；门槛抬到 0.99999 → **ESCALATE** |
| 「右下角显示桌面按钮」（不存在） | 0.4205 | 0.348 | **自然 UNDECIDED**（默认门槛就拦下） |
| 「开始菜单按钮」（不存在） | 0.5901 | 0.539 | 视门槛 |
| 「右上角关闭按钮」（不存在） | 0.9174 | 0.907 | 视门槛 |

**两条要紧的结论**：

1. **这个 4B 的读出很"尖"**：候选再同质（5 个文件夹、4 个 txt），它照样给 p≈1.0。
   所以"低置信才升级"**不是**安全网 —— 它只在**候选集里根本没有对的东西**时才降下来（上表后三行、
   以及 B 站那次的 0.4987）。**自信的错**（B 站 0.9939 那条）阈值永远拦不住。
2. 于是升级链的真实用途是：**候选集退化 / 意图与候选集不匹配时，把判断权交回大眼睛**，
   而不是"过滤错误"。大眼睛这一轮的表现：读 `65868.som.png` 自己给出 `our #4 = 发现`
   （小眼睛的 guess 恰好相同但没过它自己的门槛）→ 映射到 athand `#5` → 双击 →
   `verify: opened '发现 - 文件资源管理器'`（程序侧判据）。
